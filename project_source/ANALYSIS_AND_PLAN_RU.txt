Да. После разбора исходников я бы **немного поменял архитектурное решение относительно прошлого сообщения**: не начинать с Rudy как основного репозитория. Самый короткий путь теперь выглядит так:

> **`Keschler/cr-bot` = наш reference simulator + video/fidelity lab**
> **`cochon123/clash-royale-ai` = replay ingestion + card/t/x/y + hand reconstruction + первые policy/value baseline**
> **`cr-rudy-sim` = будущий быстрый backend для тысяч counterfactual rollouts**
> **CRForge = справочник/вторая реализация механики, когда наш движок расходится с реальной игрой**
> **KataCR = CV-движок для проверки реального видео.**

И самое приятное: `cr-bot` уже строится вокруг ровно нашей философии — реальный Clash Royale рассматривается как black-box reference, запускается тот же сценарий в симуляторе, затем ищется **first divergence**. То есть половину методологии автор уже написал за нас. fileciteturn25file0

### Особенно ценен `hand_tracker.py`

Я недооценил его раньше.

Он решает проблему неизвестной стартовой руки **точно**, перебирая все:

```text id="ekvs4x"
8! = 40320
```

возможных initial deck queues.

Для каждого наблюдаемого play он отбрасывает те starting orders, при которых эта карта не могла находиться в руке.

В результате можем получить:

```text id="juc1x9"
P(card_i in hand | all observed plays)
```

и количество возможных стартовых порядков. fileciteturn10file0

То есть проблема:

> «Но replay не сообщает initial hand»

уже фактически решена.

Для физического воспроизведения нам достаточно выбрать **любой initial order, совместимый со всей последовательностью ходов**.

Для будущей Policy-модели можно хранить распределение по возможным рукам.

# 4. Что нужно написать ДО первого реального теста

Я бы пока вообще **не трогал Policy и Value**.

Сначала надо доказать:

> `(card,t,x,y) + engine → достаточно близкий к реальности матч`.

Для этого нужны примерно пять вещей.

## Шаг 1. Canonical Replay format

Не привязываемся напрямую к Cochon:

```python id="30m42c"
ReplayEvent(
    tick=...,
    side=...,
    type="card_play",
    card="hog-rider",
    x_mtile=...,
    y_mtile=...
)
```

Матч:

```python id="m1vtfl"
ReplayBattle(
    patch=...,
    deck1=[...],
    deck2=[...],
    initial_order1=...,
    initial_order2=...,
    events=[...]
)
```

`mtile` удобно считать:

```text id="5y1lnr"
1 tile = 1000 mtile
```

Тогда arena:

```text id="31juf2"
x = 0 ... 18000
y = 0 ... 32000
```

---

# Шаг 2. Coordinate Adapter

Это надо проверить экспериментально один раз.

У Cochon:

```text id="u5heou"
18k × 32k
```

У cr-bot:

```text id="lm06d1"
18 × 32
```

Значит первичная гипотеза совершенно простая:

```python id="yzjgyp"
col = floor(x / 1000)
row = floor(y / 1000)
```

плюс, вероятно, vertical flip в зависимости от orientation:

```python id="sszvrs"
row = 31 - row
```

Это мы проверяем шестью placements:

```text id="ul1dwe"
left bridge
right bridge

bottom-left
bottom-right

top-left
top-right
```

Не надо никакой нейронки.

---

В `cr-bot` physical lab автор уже использует fixed deck order:

Никакой неопределённости.

Для обычных replay после этого используем Cochon `hand_tracker`.

# Шаг 4. ReplayExecutor

Вот это главная наша небольшая программа.

Приблизительно:

```python id="k8066d"
for event in replay.events:

    engine.advance_to(event.time)

    if event.type == "card_play":
        engine.play(
            side=event.side,
            card=event.card,
            cell=coord_adapter(event.x, event.y),
        )

    elif event.type == "ability":
        engine.activate_ability(...)
```

Но здесь нужно важное правило.

Если engine говорит:

```text id="phc9gj"
card not in hand
not enough elixir
illegal placement
```

мы **не продолжаем молча**.

Записываем:

```text id="lu2go4"
REPLAY DIVERGENCE:
tick 1428
reason: expected card not in hand
```

Потому что это уже сигнал:

> наша reconstruction неправильна раньше этого момента.

Если получим divergence, непонятно:

```text id="r9rndr"
CV неправильно увидел placement?
```

или:

```text id="917u7j"
simulator неправильно работает?
```

Поэтому:

### Test A

```text id="2oscgm"
KNOWN actions
+
REAL video observations
+
SIMULATOR
```

Проверяет **только simulator**.

И только когда это работает:

### Test B

```text id="49jh0l"
VIDEO
 ↓
action detector
 ↓
ReplayEvent
 ↓
simulator
```

Это уже end-to-end test.

# 11. Как трактовать первый divergence

Вот тут получается очень удобное дерево диагностики.

| Где расходится | Что почти наверняка проверяем |
|---|---|
| Карта сразу появляется не там | coordinate transform / placement snapping |
| Появляется позже | deploy delay |
| Сначала совпадает, потом убегает | movement speed |
| Идёт через другой мост | pathfinding |
| Сталкивается иначе | collision radius / mass |
| Выбирает другого противника | targeting / sight |
| Target правильный, но останавливается не там | attack range / hitbox |
| Стоит правильно, но стреляет раньше | load time / first hit |
| Выстрел совпал, damage позже | projectile speed |
| Timing совпал, HP нет | damage / level scaling |
| Только при толпе | collision ordering / simultaneous actions |
| Только при spell | radius / victim set / timing / pushback |
| Сначала всё хорошо, потом невозможно сыграть карту | hand cycle |
| Elixir расходится | regen rate / phase timing |
| Video и simulator разошлись, а ручной просмотр говорит simulator прав | CV bug |

# 12. Как исправляем simulator после теста

Очень важное правило:

## Никогда не подгоняем по final result.

Например нельзя увидеть:

```text id="5j4bvq"
tower HP real = 1200
tower HP sim = 1300
```

и увеличить Hog damage.

Это может случайно компенсировать совершенно другую ошибку.

Мы исправляем **только first divergence**.

Например:

```text id="py849u"
t=12.350
Hog должен был aggro Cannon
```

Тогда исследуем:

```text id="s36zct"
sight range?
building pull radius?
collision radius?
center/edge distance?
target-lock semantics?
```

Смотрим:

```text id="4i8ti9"
cr-bot
vs
CRForge
vs
Rudy
vs
реальное видео
```

CRForge, например, использует sticky target locking и edge-to-edge range с collision radii. ([github.com](https://github.com/voonhous/crforge/blob/main/docs/combat.md?utm_source=chatgpt.com))

После исправления создаём regression:

```text id="rfoc36"
test_hog_cannon_pull_001
```

И теперь эта ошибка уже никогда не должна вернуться.

# 14. Когда первый полный матч можно считать успешным

Я бы не требовал бит-в-бит сразу.

Первая цель:

### Level 1

```text id="ecdfkv"
✓ все recorded actions legal
✓ winner совпадает
✓ crowns совпадают
✓ первый decision-relevant divergence > 60 sec
```

### Level 2

```text id="qbboq6"
✓ target agreement > 95%
✓ tower hit sequence > 95%
✓ tower HP error < ~2%
✓ position p95 < 0.25–0.5 tile
```

### Level 3

```text id="x22nsj"
✓ весь матч без decision-relevant divergence
✓ timing differences ≲ one tick
✓ HP transitions совпадают
```

После Level 2 уже можно начинать экспериментировать с Policy/Value.

# 15. А потом возвращаемся к нашей AI-части

И здесь существующий код опять сильно помогает.

## Policy v0

Для начала вообще берем существующую Cochon BC policy.

Она умеет учить:

```text id="cib90d"
history
→ next card
→ placement
→ timing
```

Но сейчас она не знает полного battlefield state.

Наша модификация:

```text id="q0quc6"
ReplayEvent stream
       ↓
simulator
       ↓
S_t
       +
actual action A_t
       ↓
Policy training pair
```

Получаем:

```text id="z1v1yt"
(S_t, A_t)
```

# 16. Но Policy должна видеть НЕ весь истинный state

Это важный архитектурный момент.

Например simulator знает:

```text id="6xmean"
точный enemy elixir = 4.237
enemy hidden hand
exact attack cooldowns
```

Игрок этого не знает.

Если Policy это дать, наш coach начнёт говорить:

> «Надо было Hog right»

потому что модель «знает», что у противника Cannon не в руке.

Хотя игрок этого знать не мог.

Поэтому нужны два State:

```text id="qvn5k5"
SimulatorState
= вся истина

Public/BeliefState
= то, что мог знать игрок
```

И `cr-bot` уже построен именно так: actor получает public observation, а privileged simulator state допускается только для training critic. fileciteturn24file0

Это я бы перенял один в один.

# 17. Value

Первый Value вообще очень простой:

```text id="jirsg5"
V(public_state) → probability of win
```

Берём каждый реальный матч:

```text id="62qqim"
S_1 → WIN
S_2 → WIN
S_3 → WIN
...
```

И проигравшую сторону:

```text id="8ui767"
S_1 → LOSS
S_2 → LOSS
...
```

Так из 100 000 матчей получаются миллионы state labels.

# 18. После этого появляется настоящий Stockfish-режим

В момент реального хода:

```text id="lfatv5"
S_t
```

Policy предлагает:

```text id="j6993n"
top 20 actions
```

Например:

```text id="qen6v4"
Hog (3,17)
Hog (4,17)

Cannon (8,20)
Cannon (9,20)

Skeletons (6,21)

Wait 250 ms
Wait 500 ms
...
```

Дальше:

```text id="c7cwlb"
for action in candidates:

    S2 = clone(S)

    apply(action)

    rollout()

    score = V(S2)
```

# И именно здесь пригодится Rudy

Когда reference Python engine уже проверен относительно реальной игры, нам понадобится скорость.

У Rudy `GameState` уже `Clone`, Rust и рассчитан на огромный parallel simulation load. fileciteturn29file0 ([github.com](https://github.com/nguiaSoren/clash-royale-suite/blob/main/cr-rudy-sim/simulator/README.md?utm_source=chatgpt.com))

Тогда задача будет:

```text id="0k3d9v"
cr-bot reference engine
        │
        │ behavioral parity
        ▼
Rudy fast backend
```

И мы прогоняем одинаковый scenario suite через оба движка.

Если их state hashes/results совпадают — rollout отправляем в Rust.

# Полный roadmap в итоге

| Этап | Что делаем | Что получаем |
|---|---|---|
| **0. Assemble** | cr-bot + Cochon | simulator, video CV, replay parser |
| **1. Replay adapter** | `card/t/x/y → engine action` | воспроизведение внешних событий |
| **2. Micro fidelity** | Hog, Cannon, Musketeer tests | основные physics calibrated |
| **3. Full replay** | Hog 2.6 mirror | первый настоящий reconstructed match |
| **4. Divergence loop** | fix → regression → rerun | постепенно точный engine |
| **5. Corpus replay** | прогнать сотни Cochon matches | `S_t,A_t,result` dataset |
| **6. Policy** | BC на reconstructed public states | `π(a|s)` |
| **7. Value** | winner supervision | `V(s)` |
| **8. Counterfactual** | clone + top-k rollouts | `Q(s,a)` / regret |
| **9. Fast backend** | port/parity с Rudy | массовые rollouts |
| **10. Coach** | video/replay → errors | конечный продукт |
